# Protected PR scan revision

The required PR verifier compares each selected Code Scanning analysis to the protected selector's exact `merge_sha`. GitHub can produce two merge commit objects with the same parents and tree but different timestamps. Event checkout identity and the PR API's current `merge_commit_sha` can differ. A matching tree does not establish that the selected revision was scanned.

The PR API's `base_sha` remains a PR identity field. It can legitimately lag the selected synthetic merge's first parent. Required-mode selection schema v2 therefore separately records `merge_base_sha`: the exact first parent of the selected merge, whose second parent must be the selected PR head. The producer reads the exact `refs/heads/main` commit through the Git refs API and verifies that `merge_base_sha` is its ancestor through an exact compare request. A parent supplied by an arbitrary merge is insufficient. Missing or malformed metadata leaves selection unknown; scanners fail closed.

For protected `external-verdict` calls, `pr-ci.yml` forwards the known flag, PR number, API head/base identity, merge SHA and protected merge-base SHA to Semgrep, ESLint and govulncheck. Before checkout, each callee validates the required-main caller and repository/event identity, rereads the live PR, verifies the exact ordered merge parents, and independently proves the selected parent belongs to protected-main ancestry. Its four bounded read-only REST GETs are the PR, selected commit, exact main ref and parent-to-main compare. API head/base/merge identity must still match the selection. Unavailable or invalid proof stops the job before checkout and installation. No token permission is added.

The scanners check out the selected merge, assert actual `HEAD` and request all four SARIF uploads against it with `refs/pull/<number>/merge`. Semgrep uses the proven merge parent as its protected baseline. Ordinary calls retain their event checkout and upload identities. Standalone OSV's legacy-mode selector retains its existing API-base metadata and conservative full-scan fallback; it does not claim a required-mode merge-parent proof.

The protected final verifier requires schema v2's parent to match the locally inspected ordered parents and independently proves its protected-main ancestry. Existing protected-source, current-attempt artifact, upload-ID, selected-check and exact-SARIF identity checks remain required. Its final live PR reread still rejects head/base/merge movement during verification. There is no tree-equivalence or stale-upload exception.

Protected fork PRs follow the same checkout checks. The upstream SARIF upload action can retain event attribution for forks despite explicit ref and SHA overrides. A mismatched fork upload remains rejected by the verifier; this change makes no new fork attribution guarantee. Green offline fixtures establish the workflow contract, not successful live uploads.

1. Merge these source, tests and documentation changes through normal review and checks. The protected wrapper still pins the old reusable graph, so this step alone does not repair live scanner runs.
2. The main-owned verifier supports selection v1 only for the single immutable deployed producer `5fa007d8e1979c3368181dc6f79e3fb1c8235beb`. All its existing evidence checks remain mandatory. This narrow compatibility allows the source PR and later activation PR to be evaluated before the old pin changes; other producers cannot downgrade to v1. New required-mode producers must emit v2 with a proven merge parent.
3. In a separate reviewed PR, update the wrapper's `pr-ci.yml` pin to a commit containing this source already on protected main. Preserve the protected pin ancestry guard and all repository protections. Do not pin an unmerged candidate or weaken the verifier to make activation pass.
4. After activation, obtain fresh ordinary and required runs on each affected current dependency head. Inspect actual selected checkout/SARIF SHAs and the final verifier result. Old failed runs, armed checks and offline tests do not prove delivery. The bounded v1 compatibility can be removed in a later reviewed change after old runs no longer need evaluation.

Rollback is a reviewed source revert and pin update to a protected-main commit. Retain required checks and independent review. The old pin retains its known API-base/merge-parent failure; rollback is containment, not a readiness claim. No deployment or live-service change is performed by this workflow repair.
