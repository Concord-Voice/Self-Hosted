# Security #158 Fresh Step-Up Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close all eight findings in [Concord-Voice/Security#158](https://github.com/Concord-Voice/Security/issues/158) with transaction-bound fresh proof, own-family logout, per-family session authority, and a usable Desktop erasure flow.

**Architecture:** Self-Hosted is the canonical server implementation. Each route reserves password/MFA attempts before SQL, checks a route-specific proof against its already-locked actor in the mutation transaction, and clears the #157 MFA charge only after definite success. Desktop ships typed proof requests and a transient erasure email handoff; Hosted receives the canonical service and OpenAPI changes through the reviewed mirror.

**Tech Stack:** Go, Gin, PostgreSQL, Redis Lua, React/TypeScript, Electron IPC, Vitest, OpenAPI.

**Spec:** `docs/superpowers/specs/2026-11-14-158-fresh-step-up-design.md`

## Global Constraints

- Rebase on the exact merged Security #157 `stepup.Charge(ctx, stepup.DangerousActionBudget(redis), userID, mfaCode)` contract. One outer request owner charges a submitted nonempty code once before `BeginTx`; 429/503 fail closed. Never call Redis while holding SQL locks.
- Security #37 owns the **single** atomic free-revoke Lua reservation. This plan integrates and tests it; do not create another counter or implementation in #158.
- Use one closed, non-grace purpose per new route. Reject `step_up_token` on new #158 consumers. Keep TOTP disable's `code` and security PATCH's `current_passphrase` spellings.
- Password plus a second factor when the locked account has enrolled inline MFA is checked in the protected transaction; one-use WebAuthn inline tokens bind user, epoch, JTI, and exact purpose.
- For erasure, `confirmed_owned_server_ids` is a required sorted canonical UUID array. An unverified-email link confirms intent only; final deletion needs another fresh transactional proof.
- Preserve erasure's private-voice → family → sorted users → actor → sorted owned servers lock prefix and all confirmed/unknown-commit post-commit obligations. The account service owns proof and exact-set checks.
- No schema migration, NATS contract, deployment variable, feature flag, parallel step-up framework, speculative ownership UI, or Self-Hosted admin erasure UI.
- Run database tests only with a disposable isolated `DATABASE_URL` and `REDIS_URL`; never target shared `concord`. Use the shared default Go caches; never set `GOCACHE`, `GOMODCACHE`, or `GOLANGCI_LINT_CACHE` to private paths.
- Write only fixed outcome classes to logs/metrics/events; never log raw passwords, factor codes, inline/email tokens, request IDs, Redis key suffixes, or deep-link URLs.
- Self-Hosted and Desktop changes get separate commits/PR review; the Hosted mirror follows green canonical merge and has its own quality/security gate. Desktop support must ship before or with server enforcement.

## Review Focus

1. A concurrent server membership change after Desktop preview must return `409 owned_server_confirmation_stale` with zero erasure; Task 7 pins it.
2. A factor enrolled while a request waits for the user lock must turn password-only removal into `403`; Task 3 pins it.
3. A valid emailed link opened in another login family must not erase or mark the address verified; Task 8 pins it.
4. A duplicate/replayed deep link after a renderer reset must not arm an erase request or leak a secret; Task 12 pins it.
5. An unknown SQL commit after a free-revoke reservation must retain the reservation; Task 6 pins it against #37.
